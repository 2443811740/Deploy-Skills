# Model Version Adaptation

## 目标

把模型版本升级变成一条有证据、可回退的状态机：先从变更文档建立两个版本的契约差异，完成最小 C++ 适配并上板验收；只有结果不一致时才升级到开环分析，仍无法定位时再进入闭环 dump/replay。

## 状态机

```text
变更文档与版本基线
        |
        v
差异矩阵 -> C++ 最小适配 -> 构建部署 -> 板端结果/可视化
                                      |                |
                                      | 对齐           | 不对齐
                                      v                v
                                    收口          开环代码分析
                                                       |
                                      根因明确 --------+-------- 根因不明
                                          |                         |
                                          v                         v
                                      最小修复                  闭环数据调试
                                          |                         |
                                          +------> 板端复验 <-------+
```

## 工作产物

从 [版本适配报告模板](./assets/version-adaptation-report.md.template) 创建本次报告，持续记录版本基线、变更影响、板端验收、开环/闭环结论和异构后端证据。

## 核心原则

- 变更文档是调查入口，不是唯一事实；必须用代码、模型元数据、配置或运行证据确认。
- 先证明两个版本的契约差异，再修改 C++，不靠最终效果反向猜参数。
- 板端可视化是第一轮业务验收，但不能替代日志、raw Tensor 和结构化结果。
- 开环阶段只分析真实执行代码、配置和公式；闭环阶段才引入 dump 与输入替换。
- 每次实验只改变一个变量，并在修复后恢复全原生 C++ 路径。
- 不要求不同算法或硬件后端盲目逐位一致；先建立共同边界，再定义数值和业务阈值。

## 主流程

### 1. 读取变更文档并建立版本基线

1. 明确基线版本、目标版本、代码 revision、模型和配置哈希。
2. 收集 release notes、模型变更说明、接口表、导出记录和已知限制，并按 [变更影响矩阵](./references/change-impact-matrix.md) 记录。
3. 将每条变更标记为 `confirmed`、`assumed` 或 `unknown`。
4. 按输入/binding、前处理、模型输出、后处理、配置、标定、runtime 和结果 schema 建立差异矩阵。
5. 从变更项追踪到真实 C++ owner、配置和测试入口；未找到实现证据的条目保持 `unknown`。
6. 保存旧版本可复现的输入、输出和可视化作为基线。

### 2. 实施最小 C++ 适配

1. 每个修改必须对应差异矩阵中的一项。
2. 优先调整契约直接拥有者，避免在最终 decode 或可视化层补偿上游错误。
3. 新参数使用语义明确的名称；未配置时是否兼容旧行为必须显式决定。
4. 修改共享路径前检查所有调用方；模型专属差异优先放在独立节点或配置中。
5. 同步更新 binding、配置、消息 schema、Flow 和测试入口中受影响的部分。
6. 先执行最小静态、语法、编译或单元验证，再生成部署产物。

### 3. 上板验证与可视化验收

1. 记录并校验本地产物、板端产物、模型和配置哈希。
2. 使用固定样本执行板端原生 C++ 链路。
3. 检查退出码、错误日志、输入输出数量、schema 和关键业务字段。
4. 使用固定可视化参数与旧版本、Python 参考或已批准结果并排比较。
5. 可视化对齐且结构化指标通过时，进入最终清理；否则记录差异类别并进入开环分析。

### 4. 开环分析

不开启数据回放，先从真实执行路径逐层比较 Python BC 与 C++：

1. 输入文件、传感器集合和帧选择。
2. 图像/GDC、LiDAR、投影、栅格化和时序前处理。
3. dtype、layout、量化、binding 名称/顺序、valid/aligned shape 和 cache。
4. raw output 的反量化解释。
5. decode、过滤、坐标映射、序列化和可视化。

将两侧公式、参数、边界规则和执行分支按 [开环分析清单](./references/open-loop-analysis.md) 并排记录。根因明确时做单点修复并返回板端复验；证据仍不足或存在多个候选时，升级到闭环调试。

### 5. 闭环数据调试

1. 在 Python BC 真正的模型调用边界 dump 全部输入、raw outputs 和 manifest。
2. 在 C++/HBM 侧校验 name、dtype、shape、量化状态、哈希、padding 和 stride。
3. 先让 C++ 从文件 load 全部 Python BC dump 的参考输入并执行 HBM 推理，区分模型/runtime/后处理与本地前处理。
4. 再按图像、LiDAR、投影、地图、时序等语义组替换。
5. 对首个恢复一致的组下钻到单 Tensor 或单阶段。
6. CPU 写设备可见缓冲区后执行对应 cache clean。
7. 找到最早差异后实施最小修复，并关闭所有参考输入覆盖重新上板。

闭环阶段的完整执行规则复用 [BC/HBM 一致性 Skill](../bc-hbm-consistency/SKILL.md)。

### 6. 处理异构后端差异

使用 [异构后端对齐清单](./references/heterogeneous-backend.md) 设计三方实验。

- GDC 与 OpenCV 去畸变属于不同实现时，不默认要求像素逐位一致；先对齐标定、目标图像空间、有效 ROI、尺寸与几何映射，再评估差异对模型和最终结果的影响。
- 若 Python 前后处理使用 CUDA，而 C++ 使用 CPU，先确认两者算法契约是否相同。为隔离 CUDA kernel 的数值或实现差异，可让 Python 对应阶段显式切换到与 C++ 等价的 CPU 实现，再比较中间结果。
- 保留三方结果：Python 生产后端、Python CPU 对照、C++ 目标实现。只有 CPU 对照与 C++ 一致时，才能把剩余差异归因于异构后端。
- 如果无法获得同算法实现，则在双方共同的中间边界回放同一数据，并使用预先定义的几何、Tensor 和业务阈值，不宣称逐位一致。

### 7. 收口

1. 删除临时硬编码、强制 CPU 开关和默认开启的 dump/replay。
2. 恢复全原生 C++ 输入，重新构建和部署最终产物。
3. 重跑固定样本、边界样本和必要的连续多帧样本。
4. 记录最终根因、差异矩阵、修改项、构建/部署哈希、验收证据和剩余容差。
5. 未完成的目标端、CUDA 或 GDC 验证明确标记为残余风险。

## 升级条件

| 当前阶段 | 进入下一阶段的条件 |
|----------|--------------------|
| 文档差异分析 | 每条代码改动已有明确契约依据 |
| C++ 适配 | 最小构建验证通过且部署输入完整 |
| 板端验收 | 结果不一致并已有固定样本和基线证据 |
| 开环分析 | 真实执行路径比较后根因仍不唯一或无法由静态证据证明 |
| 闭环调试 | 找到最早差异并能用单变量实验复现 |
| 最终收口 | 全原生 C++ 路径达到约定的结构化和可视化标准 |

## 完成标准

- 版本差异矩阵完整，修改可追溯到变更项和代码 owner。
- 板端最终产物、模型和配置可由哈希确认。
- 对齐结论同时包含运行日志、结构化指标和可视化证据。
- 若使用闭环调试，最终结果不依赖 dump 或输入覆盖。
- GDC/OpenCV、CUDA/CPU 等后端差异有三方证据或明确容差，而非口头归因。
