# Alignment Skill Candidate Journal

## 目标

在每次开发任务结束时自动判断本次工作是否产生了可复用的新对齐能力。命中时，在共享评审目录中创建一个独立 Markdown 文件；未命中时不创建文件。正式 Skill 只在后续人工评审和独立验证后更新。

## 共享投递目录

1. 读取当前项目的 `.deploy/candidate-drop.conf`；忽略空行和 `#` 注释后，内容必须是唯一一个绝对目录路径。
2. 默认目录是 `/home/public/zjj/skills_pr`；可用环境变量 `DEPLOY_SKILLS_CANDIDATE_DIR` 或生成器参数 `--drop-dir` 显式覆盖。
3. 写入前确认目录存在且当前用户可写。路径缺失、配置无效或目录不可写时，报告阻塞原因并停止写入。
4. 禁止回退到项目目录、安装源仓库或其他临时日志，以免候选分散。

共享目录是统一人工评审入口。投递不要求网络、Git 仓库写权限或 Git 凭据。

## 触发时机

以下评估是使用 `.deploy` 规则完成任何开发任务后的固定收尾步骤：

1. 已完成本次任务范围内的最小可执行验证。
2. 已知道本次实际使用了哪些正式 Skill。
3. 已形成根因、有效定位方法或明确的未解决边界。
4. 在最终答复前执行候选判定。

任务尚未验证或只是提出猜想时，不能标为 `validated`；必要时可记录为 `observed`，并写清待验证项。

## 候选判定

同时满足以下条件才记录：

- **新颖性**：现有正式 Skill 没有覆盖该方法，或本次形成了实质增量，例如新触发条件、新阶段、新判别检查、新故障模式、新后端边界或更可靠的验收方式。
- **可复用性**：方法能脱离当前文件、样本和具体参数表述，至少可用于同类第二个场景。
- **可执行性**：能写出触发条件、步骤、判别检查和成功/失败证据，而不只是“注意某问题”。
- **证据性**：至少有代码证据、运行观察或实验结果；纯推测不记录。

以下情况不记录：

- 只是照已有 Skill 执行，没有改进其流程。
- 仅包含 IP、路径、模型名、Tensor index、固定参数或一次性补丁。
- 尚不能说明何时使用、如何验证或为什么有效。
- 已被正式 Skill 完整覆盖，且没有新的反例或边界。
- 与对齐、部署验证或相关调试方法无关的普通代码修改。

详细标准见 [候选评估与晋升规则](./references/evaluation-and-promotion.md)。

## 自动评估流程

### 1. 比对正式 Skill

1. 读取 `.deploy/skill-index.json`。
2. 列出本次使用或命中的正式 Skill。
3. 在相应 `SKILL.md`、references 和 scripts 中搜索本次方法。
4. 将结论分为：`covered`、`extension`、`new-skill` 或 `uncertain`。
5. `covered` 不记录；`uncertain` 先收集证据，不冒充候选。

### 2. 检查共享候选

1. 按“共享投递目录”解析路径，并扫描现有 `*.md` 候选。
2. 按 `candidate_key`、任务、`new_skill`、`proposed_target`、触发条件和可复用方法搜索同义候选。
3. 已有候选完整覆盖本次方法且没有新证据时，不创建文件。
4. 存在新边界、新反例或独立验证证据时，创建新文件并在正文中列出相关候选文件名。
5. 不修改、覆盖、重命名或删除其他使用者已经投递的文件。

### 3. 创建候选文件

1. 准备简短、可辨识的任务摘要和新技能摘要；摘要描述“做了什么”和“新增了什么能力”，不写 IP、绝对路径或凭据。
2. 从项目根目录运行生成器：

```bash
python3 .deploy/skills/governance/alignment-skill-journal/scripts/create_candidate.py \
  --task "<任务摘要>" \
  --skill "<新技能摘要>" \
  --evidence-level <observed|validated|repeated>
```

3. 文件名由脚本生成为 `<任务摘要>__<新技能摘要>__<UTC时间>.md`；同一秒同名时自动增加 `__NN` 后缀。脚本使用排他创建，绝不覆盖已有文件。
4. 只编辑生成器返回的新文件，并补全以下内容：

- 稳定 `candidate_key`、建议动作、目标 Skill 和已检查的正式 Skill
- 触发条件与不适用条件
- 可复用问题、方法和最便宜的判别检查
- 验证证据、失败证据和剩余风险
- 相关候选文件名（如有）
- 项目专属事实与可泛化规则的分离
- 晋升前仍需补充的验证

5. 候选可以保留项目相对路径和 sanitized 命令作为证据，但禁止密码、令牌、私钥、真实凭据或不必要的设备地址。

### 4. 任务收尾

- 创建并补全后，在最终答复中简短说明新候选文件路径。
- 没有候选时不创建文件，也不生成“无候选”记录。
- 不因记录候选而改变本次任务的正式实现或验证结论。

## 证据等级

| Level | 含义 |
|-------|------|
| `observed` | 已观察到可复现现象或判别价值，但修复/完整验证尚未完成 |
| `validated` | 方法已通过本次任务的可执行验证 |
| `repeated` | 在至少两个独立任务或场景中得到验证 |

## 候选生命周期

```text
candidate -> review-ready -> promoted
          \-> rejected
```

- `candidate`：首次记录，证据至少为 `observed`。
- `review-ready`：方法已验证、内容完整且完成去重。
- `promoted`：已提炼到正式 Skill，并记录目标文件和版本。
- `rejected`：不具通用性、已重复、证据不足或方向过时，保留原因避免重复发现。

## 晋升约束

晋升不是日常开发任务的自动动作。定期提炼时必须：

1. 再次检查正式 Skill 和所有待评审候选。
2. 删除 IP、绝对路径、模型名、固定 index 和一次性参数。
3. 将项目证据改写成通用触发、步骤、判别检查、验收和限制。
4. 更新目标 Skill、索引、版本、README/DEPLOY 清单和对应验证。
5. 将候选文件状态标记为 `promoted`，记录目标和版本；不要静默删除审计信息。

## 完成标准

- 每次开发结束都执行了候选判定。
- 只有真实新颖且可执行的对齐经验进入共享目录。
- 每个候选使用独立、描述性文件名，创建时绝不覆盖已有文件。
- 已有候选完整覆盖时不重复投递；新证据用新文件记录并关联已有候选。
- 所有安装项目按 `.deploy/candidate-drop.conf` 写入同一个共享评审目录。
- 候选记录足够详细，后续无需恢复完整聊天历史即可评审。
